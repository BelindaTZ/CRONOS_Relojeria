# Convenciones de código — CRONOS

Referencia rápida de las reglas de la Constitución (`.specify/memory/constitution.md`, Principios V, X, XI, XII) aplicadas al repositorio. Toda feature 001+ replica esta estructura; no la redefine.

## 1. Nomenclatura

| Ámbito | Estilo | Ejemplos |
|---|---|---|
| Python / SQL (backend) | `snake_case` | `permiso_operacion`, `ping_storage()`, `rol_id` |
| Tablas y columnas PostgreSQL | `snake_case` | `permiso_modulo`, `creado_en` |
| JS / Vue (frontend) | `camelCase` | `useHealth()`, `healthApi.js`, `opcionesExportacion()` |

## 2. Arquitectura por capas (backend)

Cada módulo de negocio vive en `backend/src/<modulo>/` con estas capas:

```
<modulo>/
├── router.py      # solo HTTP: rutas, validación de request/response, códigos de estado. SIN lógica de negocio.
├── service.py     # reglas de negocio, orquestación, transacciones.
├── repository.py  # acceso a datos (SQLAlchemy). SIN reglas de negocio.
└── schemas.py     # modelos Pydantic de entrada/salida del módulo.
```

- Los routers **no** contienen lógica de negocio (Principio X).
- El backend expone **solo** REST/JSON; nunca renderiza HTML (Principio V).
- `backend/src/shared/` contiene lo reutilizable: `config`, `database`, `storage`, `exceptions`, `schemas`, `pagination`. Nada de "cajón de sastre".

El módulo `health/` es la **plantilla canónica**: las features nuevas lo copian como punto de partida.

## 3. Arquitectura por módulos (frontend)

Cada módulo de negocio vive en `frontend/src/<modulo>/`:

```
<modulo>/
├── components/     # componentes Vue del módulo
├── composables/    # lógica reactiva reutilizable dentro del módulo
├── stores/         # stores Pinia del módulo (si aplica)
└── services/       # llamadas a la API de ESTE módulo
```

- **Ninguna** llamada `fetch`/HTTP vive fuera de una capa `services/` (Principio V/X). Todas usan el cliente único `frontend/src/shared/api/client.js`.
- `frontend/src/shared/` contiene componentes UI, utilidades y helpers reutilizables.
- El módulo `health/` es la plantilla canónica del frontend.

## 4. Modularidad (Principio X — NON-NEGOTIABLE)

- Cada módulo tiene una **frontera clara**. Un módulo depende de `shared/` y de la **API pública** de otros módulos, **nunca** de sus archivos internos.
- **Prohibido**: `from src.otro_modulo.repository import ...`, `import ... from '@/otroModulo/stores/...'`.
- Todo lo compartido por 2+ módulos vive en `shared/` y se importa desde ahí — no se copia ni se duplica (DRY).
- Añadir un módulo nuevo **no** obliga a tocar archivos de otro módulo; a lo sumo se añade una línea al registro de rutas (`backend/src/main.py`, `frontend/src/router/index.js`).
- Verificación automática: `frontend/scripts/check_module_boundaries.mjs` y `backend/tests/test_module_boundaries.py`.
- **Frontend**: un módulo que consume a otro importa SOLO desde su `@/<modulo>/index.js` o `@/<modulo>/routes.js` (API pública), nunca de `components/` o `services/`. Ej.: `usuarios` importa `listarRoles` desde `@/rbac`, no desde `@/rbac/services/rbacApi`.

## 4.1. Modelos ORM del sustrato central (`backend/src/shared/models.py`)

Las tablas de **identidad, RBAC, configuración y auditoría** (`usuario`, `rol`, `modulo`, `operacion`, `permiso_*`, `sucursal`, `medio_pago`, `parametro_configuracion`, `registro_auditoria`, …) se definen como modelos ORM en **un único** `shared/models.py`. Es infraestructura compartida: el `guard`, la `auditoria` y el motor de `parametros` los consumen de forma transversal, y ninguno de esos puede depender de un módulo de negocio (viola la dirección de dependencias). Los módulos `auth`/`usuarios`/`rbac`/`sucursales`/`configuracion` construyen su lógica router→service→repository **encima** de estos modelos; no redefinen el esquema. Esto NO es un modelo monolítico de negocio: el esquema operativo (relojes, ventas, OT…) sigue naciendo por feature, cada uno con su `data-model.md` y su migración.

El esquema físico lo crean las migraciones Alembic **a mano** (`0001`–`0006` y las siguientes). Los modelos de `shared/models.py` deben mantenerse consistentes con ellas manualmente (no se usa `--autogenerate`).

- **Exportación**: `frontend/src/shared/exportar.js` (`opcionesExportacion()` → CSV / Excel / PDF).

## 6. Configuración y secretos (Principio IX)

## 7. Migraciones

- Alembic incremental: **cada feature aporta su propia migración**. No hay `01_operativo_postgres.sql` monolítico.
- `0001_rbac_base` (feature 000) crea el esquema base de RBAC vacío. `0002`–`0006` (feature 001): `usuario`/sesión, `permiso_usuario` + siembra de `modulo`, `sucursal` + `usuario_sucursal`, catálogos, `parametro_configuracion` + `registro_auditoria` (con trigger de inmutabilidad append-only). `0007_proveedores` (feature 002): `proveedor`(+tipos/documentos/calificación), `orden_compra`(+líneas), `recepcion_compra`(+líneas), `compra_programada`.
- Modelos ORM de módulo: cada feature de negocio pone sus modelos en `backend/src/<modulo>/models.py` (no en `shared/models.py`, que es solo el sustrato central). `alembic/env.py` los importa para tener `Base.metadata` completo.
- Scheduler in-proceso (APScheduler): las tareas recurrentes ligeras (compras programadas de 002; gastos recurrentes de 010) usan un `BackgroundScheduler` arrancado en el `lifespan` de `main.py`, con un endpoint `POST /_internal/scheduler/tick` para forzarlo en pruebas/operación. **No** se usa Airflow (reservado a 012, Const. Ppio VII).
- Toda migración es idempotente en la práctica: `alembic upgrade head` dos veces no produce cambios; `alembic downgrade base` limpia sin residuos.

## 7.1. Autorización y scoping en las features 002+

- Todo endpoint de negocio declara su permiso con `Depends(require_perm("<modulo>", "<operacion>"))` de `shared/guard`. Una prueba de contrato (`backend/tests/test_endpoints_declaran_permiso.py`) falla si algún endpoint no lo hace. Excepciones permitidas: `/health`, login y flujos de recuperación de acceso, y el autoservicio del propio usuario (`get_current_user_full_scope`).
- Alcance de datos: cada endpoint declara su modo — `consolidado` (sin scoping), `propia sucursal` (`scope_sucursal(stmt, user, <campo_sucursal_id>)`) o `solo propios` (`scope_propiedad(stmt, user, <campo_owner_id>)`). Gerencia General ve consolidado en ambos. Un usuario sin sucursal asignada no puede ejecutar operaciones "propia sucursal" (el guard lanza 403).
- Configuración (`configuracion`): además del permiso, `Depends(require_gerencia_o_delegado)` — solo Gerencia General o un delegado explícito (override `conceder` sobre el módulo `configuracion`).
- "Rol elevado" (correcciones auditadas de 002 en adelante): `proveedores.service.es_rol_elevado(user)` → `"Gerencia General"` o `"Gerente de Sucursal"` en `user.roles`. Se usa para editar `razon_social`/`ruc_nit` de un proveedor con historial y para `PATCH /ordenes-compra/{id}` (corregir compra recibida), siempre con `motivo` + auditoría antes/después.
- Extensión entre features: 002 expone `proveedores.service.registrar_receptor_inventario(fn)` para que 003 reciba el evento de recepción (alta de unidades / stock / lote perecedero). Mientras 003 no existe, la propagación es no-op.

## 10. Componentes de UX compartidos (`frontend/src/shared/ui/`)

Toda pantalla de datos maestros usa estos componentes — no se reinventan tablas ni se usan `window.*` ni `prompt()` encadenados:

- **`WorkPanel.vue`** — panel de trabajo estándar (Principio XI): encabezado (eyebrow oro + título serif + acción primaria) → `KpiStrip` opcional → toolbar (búsqueda reactiva multi-criterio + `#toolbar` para filtros) + conteo → tabla (`columns` + slots `#cell-<key>` + acciones por fila vía `rowActions(row)`) → paginación → estados vacío / error / cargando (skeleton).
- **`KpiStrip.vue`** — 2–4 métricas en una tarjeta con celdas hairline; la cifra "cabecera" puede ir en oro.
- **`FormModal.vue`** + **`FormField.vue`** — alta/edición multi-campo (grid 2 col), footer Cancelar/Guardar con spinner, Esc cierra.
- **`ComboBox.vue`** — escribir → filtrar → seleccionar de opciones de la BD (Principio XI: nunca deja un valor inexistente). **`CheckList.vue`** — selección múltiple (roles, sucursales, tipos).
- **Acciones por fila** — `WorkPanel` pinta una columna **"Acciones"** al final con los botones aplicables representados por un icono (`a.icon`) y su descripción en `title`/`aria-label` (tooltip al pasar el ratón). `rowActions(row) => [{ label, icon, danger, hidden, disabled, onClick }]`. Las destructivas van con `danger: true` (hover rojo). (`RowMenu.vue` — kebab "⋮" — queda como componente disponible pero `WorkPanel` ya no lo usa.)
- **`Pill.vue`** — insignia de estado (`tone`: neutral/good/warn/bad/info), con punto + texto (nunca color solo).
- **`toast.js`** + **`ToastHost.vue`** — feedback efímero (`toast.success/error/info`), auto-dismiss 4s (error 6s), `aria-live`.
- **`DialogHost.vue`** (montado 1× en `App.vue`) — `confirm()`/`prompt()` de `dialogs.js`; `tone: 'danger'` pinta icono de alerta + botón rojo, y el mensaje **debe** decir la consecuencia, no solo "¿Seguro?".
- **`CrIcon.vue`** — set de iconos trazo Lucide inline (sin emoji, sin CDN).

Toda acción destructiva (inactivar, cancelar, desactivar) pasa por `confirm({ tone: 'danger' })`. La contraseña temporal de un usuario nuevo la **genera el sistema** y se muestra una sola vez.

## 11. Inventario y piezas (feature 003)

- **Dos módulos**: `inventario` (relojes unidad física + calibres + historial de serie + alertas de stock + valor) y `piezas` (repuestos/insumos + stock por sucursal + lotes/caducidad + movimientos). `calibre` es de `inventario`; `piezas` lo consume solo por su API pública (`from inventario import calibres_por_ids`). Alertas de stock (de modelo Y de pieza) viven en `inventario`; `piezas` llama `inventario.recalcular_alertas_pieza(...)`.
- **Stock nunca negativo (Principio II)**: `piezas.service.aplicar_movimiento` bloquea la fila `stock_pieza` con `SELECT … FOR UPDATE` y aborta (`stock_insuficiente`, 409) si el resultado sería < 0. Además la tabla tiene `CHECK (stock_actual >= 0)`. `movimiento_stock_pieza` es append-only (trigger DB).
- **Historial inalterable**: `evento_serie` append-only (trigger DB). Se escribe con `inventario.repository.registrar_evento`; otras features usan `inventario.registrar_evento_externo(...)` para venta (009) / servicio (008) / baja (011). Nunca hay endpoint de edición/borrado de historial.
- **Costo/margen restringido**: `puede_ver_costos(user)` (rol administrativo) — la respuesta lleva `costos_visibles: bool`.
- **Fotos**: bucket `reloj-imagenes` vía `shared.storage` (subida por el backend, nunca directa del navegador). Papeles del Full Set → bucket `documentos`.
- **Recepción de compra → inventario**: `main.py` hace `proveedores.registrar_receptor_inventario(piezas.recibir_de_compra)`. Piezas suben stock automáticamente; relojes quedan en `GET /relojes/pendientes-recepcion` para fichar unidad por unidad con su N.º de serie.
- **Parámetros §9.2**: `stock_maximo_modelo` (12), `umbral_reposicion_relojes` (1), `umbral_reposicion_piezas` (0), `umbral_caducidad_dias` (30) — sembrados en `0009_inventario`, editables en Configuración · Parámetros, consumidos por el recálculo de alertas.

## 12. Traslados entre sucursales y visibilidad por sucursal (feature 004)

- **Módulo `traslados`** (`backend/src/traslados/`, clave RBAC `multisucursal`). Máquina de estados de la transferencia: `en_preparacion → en_transito → recibida|parcial`; `en_preparacion|en_transito → cancelada`. `recibir` toma lock de la fila (idempotente ante doble confirmación → 409).
- **Efecto en el inventario** siempre en la misma transacción y **vía API pública de 003** (nunca tocando sus tablas): `inventario.marcar_reloj_en_transito` / `recibir_reloj_transferido` / `revertir_reloj_transferencia`; `piezas.mover_stock_traslado(transferencia_salida|transferencia_entrada)`. Un reloj `en_transito` no cuenta para el conteo de modelo ni aparece en los listados `disponible`; las piezas en tránsito no cuentan para el stock de ninguna sucursal.
- **Discrepancia en recepción**: `cantidad_recibida < enviada` ⇒ `discrepancia_transferencia` + `accion_merma` (causa `dano_transito`) para la feature 011. El faltante no reingresa a stock.
- **Scoping por sucursal (FR-008, Principio IV/VI)**: helper único `inventario.sucursales_visibles(user, sucursal_id)` — Gerencia General = consolidado (o filtra por `sucursal_id`); otros roles = solo sus `sucursal_ids`. Aplicado en `inventario` (`/relojes`, `/valor-inventario`) y `piezas` (`/piezas`, `/piezas/lotes`, `/piezas/valor`) y en `traslados`. No se reimplementa el filtro por módulo (DRY).
- **Navegación agrupada**: `AppShell.vue` colapsa las categorías en menús desplegables (Abastecimiento / Inventario / Sistema) cuando superan ~9 entradas (Principio XI: mega-menú para 4+ sub-opciones). El grupo se marca activo (filete de oro) si una de sus rutas hijas lo está.

La vista muestra nombre (identificación) e IP.
- **`/perfil`**: la vista se rehízo con el sistema de componentes; el correo se muestra en "Datos de la cuenta" (no solo en el formulario de edición); la foto de perfil se ve en la tarjeta y en el círculo de la barra de navegación (`session.fotoPerfil`); cambiar contraseña es un `FormModal` con los 3 campos (actual/nueva/repetir) visibles a la vez.

## 22. Retrofit multi-rol (2026-09-10) — los 5 roles de negocio, de verdad usables

Hasta este punto **todo** el frontend (features 001-010) estaba, de hecho, detrás de un único candado: `meta.soloGerencia` en cada ruta + `if (session.esGerencia)` envolviendo las 10 categorías de nav. Cualquier rol que no fuera literalmente "Gerencia General" veía solo "Panel" y "Mis datos" — un atajo de desarrollo nunca corregido, detectado por el usuario ("hasta ahora hemos probado solo como gerente general — ¿qué hay de los demás roles?"). El backend, en cambio, ya traía bastante lógica real por rol (scoping de técnico, `_ROLES_VER_COSTOS`/`_ROLES_JEFE`, `sucursales_visibles`) — nunca ejercitada desde la UI. Se decidió corregirlo **antes** de 011, no al final de las 15 features.

- **Migración `0024_roles_negocio`**: siembra los 5 roles de negocio de la Constitución §3 —además de "Gerencia General", que sigue naciendo de `scripts/seed_gerencia.py`, no de una migración— con una matriz de permisos por defecto (módulo × operación) derivada de la tabla ilustrativa §3.1 de `especificacion_sistema_relojeria.md` y extendida a los módulos que esa tabla no cubre. **Gerente de Sucursal**, **Vendedor**, **Técnico**, **Técnico Jefe**, **Contador** — descripciones y matriz completa en el propio archivo de migración. Idempotente por `nombre` (`ON CONFLICT DO UPDATE` + reemplazo limpio de `permiso_modulo`/`permiso_operacion`): reconcilia un rol homónimo creado a mano en una sesión de prueba anterior (así se corrigió el "Vendedor" de pruebas que solo tenía `citas`+`proveedores` y ni siquiera `ventas`).
- **`shared.guard.permisos_efectivos(db, user)`** (nuevo): módulos accesibles + operaciones permitidas ya resueltas (roles + excepciones `permiso_usuario`) — el mismo cálculo que hace `require_perm` en cada endpoint, expuesto para que el FRONTEND sepa qué pintar. Gerencia General usa un atajo (todos los módulos/operaciones) en vez de recorrer 15×4 checks. **`PerfilOut.permisos: dict[str, list[str]]`** nuevo en `GET/PATCH /perfil` (`usuarios/service.py::get_perfil`/`update_perfil` ahora reciben el `CurrentUser` completo, no solo el id, para poder calcularlo).
- **`contabilidad.service.puede_gestionar_contabilidad(user)`** (nuevo, reemplaza el uso de `es_gerencia` en gastos/CxP/periodos): `{"Gerencia General", "Contador"}` — Const. §3 dice explícitamente que el Contador administra "módulo contable, cuentas por cobrar/pagar, gastos"; el `es_gerencia` estricto de la implementación original de 010 era un gap real, no una decisión. `es_gerencia` se conserva para lo que sí sigue siendo prerrogativa exclusiva del propietario (ninguno dentro de `contabilidad` por ahora).
- **Frontend — predicado único** `shared/rbacNav.js::puedeEntrar(session, meta)`, usado tanto por el guard de navegación (`router/index.js`) como por `AppShell.vue` (para que el nav nunca ofrezca un enlace que el guard vaya a rebotar). `meta` de cada ruta acepta 3 llaves, ya no solo `soloGerencia`:
  - `soloGerencia: true` — reservado a Sistema (usuarios/roles/sucursales/configuración/parámetros/auditoría) + pantallas de política pura que el backend gatea con `require_gerencia_o_delegado` (niveles de fidelización, descuentos, cupones, margen mínimo, facturación→puntos de emisión).
  - `modulo: '<clave>'` (+ `operacion` opcional) — gate RBAC real vía `session.puede(modulo, operacion)`; es lo que reemplazó `soloGerencia` en el resto de las ~55 rutas de negocio (citas, ventas, proveedores/compras, inventario, piezas, taller/OT, lubricación, clientes, contabilidad, traslados).
  - `roles: [...]` — conjunto de rol explícito para pantallas de costos/política que no mapean 1:1 a una operación RBAC (mismos conjuntos que ya usa el backend: `valor-inventario`→`_ROLES_VER_COSTOS`; `reglas-bono`→`_ROLES_JEFE`; `bonos-periodo`/`informe-servicios`→`_ROLES_VER_COSTOS`∪Técnico Jefe).
  - `session.js` ganó el getter `permisos` (de `perfil.permisos`), la action `puede(modulo, operacion?)`, y los getters `puedeVerCostos`/`esJefeTecnico` (mismos conjuntos de rol que el backend, para las pocas pantallas gateadas por `roles`).
- **`AppShell.vue`**: la categoría "Sistema" queda oculta salvo Gerencia General (todos sus hijos son `soloGerencia`); las demás categorías se arman filtrando cada `hijo` por `visible(nombreRuta)` (resuelve la `meta` real de esa ruta vía `router.getRoutes()`) y se ocultan por completo si ningún hijo sobrevive el filtro.

Cada dominio declara `modo` (`"incremental"`, con `%(watermark)s` sobre una columna `updated_at`/`creado_en`/`fecha` fiable del origen; o `"full"`, reextracción completa cada corrida) y `tabla_destino` (`wh.fact_*`/`wh.dim_*`, `ReplacingMergeTree` por clave + `updated_at`). **Añadir un dominio nuevo (feature futura) = agregar UNA entrada a `config.py`** con su SQL y su tabla destino (ya creada en `warehouse/ddl/`) — nada más se toca (Spec §FR-018).

El resto son `"incremental"`.
  - `movimientos_inventario` unifica `evento_serie` (relojes) + `movimiento_stock_pieza` (piezas) por `UNION ALL`; `fact_movimiento_inventario` usa `(tipo_bien, movimiento_id)` como clave compuesta porque las dos secuencias de origen empiezan en 1 (colisionarían solas).

- **Motor genérico de carga por tipo de columna** (`data/lib/load.py::_convertidor`): en vez de mapear a mano el tipo de cada campo de cada dominio, `load.py` hace `DESCRIBE TABLE <tabla_destino>` en ClickHouse y deriva el conversor (Decimal/DateTime/Date/Int/String, con o sin `Nullable`) desde el tipo real de la columna — un dominio nuevo no necesita tocar esta función.
- **`transform_<dominio>`** existe como tarea observable (Spec §FR-005) pero, dado el diseño "un dominio = una consulta ya denormalizada", no hace una agregación adicional — es un punto de extensión explícito. Los 18 modelos de reporte de §4.11.2 son **VISTAS planas** (no `MATERIALIZED VIEW`) sobre los hechos/dimensiones ya cargados (`warehouse/ddl/040_views_reportes.sql`): a este volumen de negocio una vista calculada al vuelo ya cumple el objetivo de rendimiento del plan (<3 s) y es más simple de mantener — simplificación dentro de lo que `data-model.md` ya dejaba abierto ("vista o `MATERIALIZED VIEW`"). Todas filtran los estados anulados/cancelados donde aplica (Spec §FR-013) y leen con `FINAL` para resolver la versión vigente de `ReplacingMergeTree`.
- **Landing-zone**: `<dominio>/<run_id>/<dominio>.ndjson` (NDJSON, no parquet — cero dependencias nuevas tipo pyarrow, formato admitido por `data-model.md` sin ese costo). `load_wh` **descarga de `landing-zone`, nunca reutiliza el archivo local del `extract`** — el contrato ELT literal es que Load warehouse lee de la zona de aterrizaje. Retención parametrizable (`LANDING_ZONE_RETENCION_DIAS`, semilla 30) vía la tarea `landing_zone_retencion` del propio DAG (corre en cada corrida, idempotente — nada que borrar fuera de rango).
- **Control del pipeline en ClickHouse** (`ctl.pipeline_watermark`/`pipeline_corrida`/`pipeline_frescura`) — no en la DB de metadata de Airflow, para que `GET /reportes/estado-frescura` solo necesite un cliente de ClickHouse, no acceso a la base interna de Airflow.
- **`backend/src/reportes_estado/`** (único punto de contacto con el backend operativo, `contracts/pipeline-estado.openapi.yaml`): `GET /reportes/estado-frescura` y `POST /reportes/actualizar-ahora`, gateados por `require_perm("reportes","consultar")` (clave RBAC ya sembrada en `0003`; Gerente de Sucursal/Técnico Jefe/Contador la tienen desde `0024`). El backend **nunca** abre ClickHouse/Airflow al arrancar ni en `/health` (research D7) — ambos se conectan de forma perezosa dentro del propio endpoint, con `try/except` que degrada a `disponible: false` (frescura) o `503 DependencyUnavailableError` (disparo manual) en vez de un 500. `actualizar-ahora` primero consulta si ya hay una corrida `running` en Airflow (`409 ConflictError` si la hay) antes de disparar una nueva.
- **Tests**: `backend/tests/test_operativo_resiliente.py` (US1, T008) y `test_estado_frescura.py` (US4, T024) corren en la suite normal de `backend/tests` (sin ClickHouse/Airflow en ese entorno — confirman degradación limpia + el gating RBAC). `data/tests/` (T013/T018/T023/T027) son de integración contra el stack real — corren dentro del contenedor `airflow-scheduler` (`docker compose exec airflow-scheduler pytest /opt/airflow/tests -q`), se saltan (no fallan) si ClickHouse/PostgreSQL no responden. Cubren: el rol de solo lectura no puede escribir (DP001/DP002), una extracción incremental y una `"full"` no fallan, una recarga no duplica filas y la versión más nueva gana (`ReplacingMergeTree`), el watermark avanza y se relee, y los 18 modelos de §4.11.2 existen y son consultables.
- **Respaldo** (Spec §FR-015): `data/scripts/backup_warehouse.sh <destino>` — `BACKUP DATABASE` nativo de ClickHouse (disco `backups` configurado en `data/clickhouse/config.d/backups.xml`) + copia de `dags/`/`warehouse/` + export de variables de Airflow. Sin cron automático en dev (research D9) — se corre a mano o desde un cron externo del anfitrión.
- **Cómo añadir un dominio nuevo** (para features futuras, Spec §FR-018): (1) confirmar que la tabla de origen tiene una columna de actualización fiable — si no, el dominio nace `modo="full"`; (2) si hace falta una tabla de hechos/dimensión nueva, agregarla a `warehouse/ddl/030_fact_tables.sql` o `020_dim_tables.sql` (`ReplacingMergeTree(updated_at)` por convención); (3) agregar la entrada a `DOMINIOS` en `data/dags/config.py` con el SQL ya denormalizado al grano de esa tabla; (4) si el dominio alimenta un reporte de §4.11.2 nuevo (o una feature futura con sus propios reportes), agregar la vista a `040_views_reportes.sql`; (5) reconstruir la imagen de Airflow y de ClickHouse (`docker compose up -d --build`) — el DAG recoge el dominio nuevo automáticamente en la próxima corrida, sin tocar `elt_operativo.py`.

## 26. Dashboards y reportes (feature 013)

Fachada de lectura pura sobre el warehouse de 012 — `backend/src/dashboards/` no tiene tablas propias (`data-model.md` de 013 lo deja explícito). `shared/clickhouse.py` (extraído de `reportes_estado`, 012, para reuso — Ppio X) es el único punto de conexión al warehouse; import perezoso, nunca al arrancar.

- **Catálogo de 18 reportes** (`dashboards/warehouse.py::CATALOGO`, `assert len == 18`): cada uno declara `modelo_ch` (la vista de ClickHouse de 012 que lo alimenta), `filtros_soportados` — **fijados por las columnas que la vista REALMENTE tiene** (no todas admiten periodo/sucursal/marca/técnico: `valor_total_inventario`/`aging_cxc_cxp`/`clientes_por_nivel` son fotos del estado actual, sin columna de periodo) — y, para los que llevan gráfico, `col_categoria`/`cols_series` explícitos (no se infiere el eje/serie de forma genérica: más código, pero correcto por construcción).

Resuelto con el namespace **`/reportes/analitico/{slug}`** — evita la colisión y además comunica la diferencia real: "operativo, ya construido en una feature anterior" vs. "analítico, desde el warehouse".
- **`/panel` es más estricto que "reportes:consultar"**: el contrato dice literalmente "Solo Gerencia General" para el panel — se gateó con `require_gerencia_o_delegado` (no `require_perm("reportes","consultar")`, que Gerente de Sucursal/Técnico Jefe/Contador también tienen desde `0024` y hubiera dejado a un Gerente de Sucursal abrir el panel consolidado). Cualquier otro rol: si pide una sucursal fuera de las suyas, `403`; si no pide ninguna, se limita a las suyas (`IN`, no `=`, por si tiene varias). Verificado contra el stack real: una Gerente de Sucursal demo con datos en dos sucursales solo ve la suya en `valor-total-inventario`, y pedir la otra explícitamente da `403`.
- **`shared/exportar.js` dejó de ser un stub**: seguía siendo el stub literal de la feature 000 (`console.warn`, ningún archivo se descargaba) — y **14 pantallas de 003, 005, 006, 007, 009, 010 y 011 ya lo llamaban** esperando una implementación real. Paleta categórica fija (`primary-600, gold-600, tertiary-600, neutral-400, primary-400, gold-300`), grid mínimo (solo líneas discontinuas tenues), remate en oro en líneas. `productividad-tecnico` solo grafica `ordenes_completadas` — `margen_generado` es otra unidad (moneda vs. conteo) y mezclarlas habría sido un eje doble encubierto (dataviz: "never dual-axis"); el margen se ve en la tabla de detalle, que trae todas las columnas igual.

## 27. Notificaciones automatizadas por email (feature 014)

Módulo completo de cola + seguimiento + reintentos + opt-out + plantillas editables sobre la capacidad compartida de correo de 001 (`shared/correo`). Migración **`0030_notificaciones`**.

- **`PlantillaEmail` vive en `shared/models.py`, NO en `notificaciones/models.py`** — decisión de arquitectura real, no solo de conveniencia: `shared/correo/service.py::render()` necesita leerla para CUALQUIER correo del sistema (no solo los de 014), y `shared/` nunca puede depender de un módulo de negocio (Ppio X) — importar `PlantillaEmail` desde `notificaciones.models` habría invertido la dependencia (y habría sido un import circular real en cuanto `notificaciones` importa `shared.correo`, que sí hace). Mismo criterio que `CategoriaGasto`/`CategoriaMerma`: una tabla "editable por Gerencia" que una capacidad de `shared/` necesita leer, vive en `shared/`.
- **Las 10 plantillas que ya existían (001/008/009/010/011) NO se sembraron en `plantilla_email`** — desviación deliberada de `data-model.md` ("plantillas sembradas"). `plantilla_email` es un **override opcional**: `render()` primero busca una fila `activa=true` para ese `tipo` (índice único parcial garantiza como mucho una); si no hay ninguna, sigue usando el archivo Jinja2 de `shared/correo/templates/` de siempre. Sembrar las 10 plantillas completas en la migración habría duplicado HTML grande con riesgo real de que archivo y BD divergieran — con el override, Gerencia edita solo lo que de verdad quiere personalizar, y todo lo demás sigue siendo la única fuente de verdad de antes.
- **Solo 2 disparadores de OT nuevos, no uno genérico por cada transición**: 008 ya tenía 4 correos síncronos, ya probados, para `tecnico_nueva_ot`/`tecnico_asignado`/`diagnostico_cliente`/`servicio_listo_retiro` (el último cubre el estado `listo`) — se dejaron **intactos**, sin moverlos a la cola, para no arriesgar código que ya funciona. Lo que 014 agrega de verdad son los 2 estados que hasta ahora quedaban completamente mudos — `entregado` (el cliente nunca recibía ni un recibo) y `cancelada` — como disparadores NUEVOS y SÍ encolados (`_avisar_ot_estado` en `servicio_tecnico/service.py`).
- **El recordatorio de cita usa el punto de integración que 007 ya había dejado preparado**, no un `encolar(programar_para=fecha−antelación)` en `citas.confirmar()` (la primera implementación, descartada): `citas/service.py::citas_para_recordatorio(antelacion)` ya existía con el comentario literal `# ============================================================ API pública (008/009)` y `"""Interno (014): citas confirmadas cuya hora cae dentro de [ahora, ahora+antelación]."""` — 007 ya había anticipado exactamente esta integración. `notificaciones/scheduler.py` la sondea en cada tick (junto con `procesar_cola()`) y `encolar()` deduplica por `(cita_id, fecha_confirmada)`, así que sondear cada minuto no reenvía nada. `citas.cancelar()` además llama `cancelar_pendiente()` como red de seguridad por si un recordatorio ya se había encolado en el margen de un tick antes de la cancelación.
- **Nivel sube — nunca baja silenciosa**: `clientes.recalcular_nivel()` solo encola el correo cuando `nuevo.orden > anterior.orden` — un descenso de nivel (que también pasa por la misma función) no genera ningún correo, coherente con que la spec solo pide avisar "cuando el cliente asciende".
- **Opt-out nunca bloquea el hecho que originó el correo**: `clientes.crear_cupon()` sigue creando el cupón aunque `encolar()` devuelva el `envio` en `cancelado` por `opt_out` — verificado con un test dedicado (`test_opt_out_no_bloquea_la_creacion_del_cupon`). Los 4 tipos críticos (`password_temporal`, `usuario_bienvenida`, `ot_entregado`, `ot_cancelada`) rechazan el intento de opt-out con 422 desde `set_preferencia()` — son avisos operativos, no de marketing/fidelización.
- **Worker in-proceso, sin Airflow** (Ppio VII — 012 es la única feature con Airflow): `notificaciones/scheduler.py`, APScheduler, cada 1 minuto (Spec SC-001: aviso de OT en menos de 1 minuto), mismo patrón que `proveedores`/`contabilidad`. Reintentos con backoff (`backoff_email_minutos × intentos`) hasta `max_reintentos`; `POST /_internal/notificaciones/scheduler/tick` para forzarlo en pruebas/operación.
- **Conciliación de webhooks por prefijo**: SendGrid le agrega un sufijo por destinatario al `X-Message-Id` que devuelve al enviar — el evento del webhook trae `sg_message_id = "<message_id>.<sufijo>"`, así que `repository.por_proveedor_message_id_prefijo()` concilia por el prefijo antes del primer punto, no por igualdad exacta.
- **Gap de seguridad documentado, no bloqueante**: `POST /webhooks/email` NO valida todavía la firma ECDSA del Event Webhook de SendGrid (requiere una clave de firma que el negocio no ha configurado en `.env`) — está en el router como comentario explícito. Peor caso hoy: un tercero podría marcar un `envio` propio como `entregado`/`rebotado` adivinando un `proveedor_message_id`; nunca escribe sobre datos operativos ni dispara un envío nuevo. Pendiente para cuando el negocio active y comparta la clave de firma.
- **Verificación — disciplina real con SendGrid activo en este entorno de dev**: `EMAIL_BACKEND=sendgrid` sigue configurado en `.env` desde una sesión anterior, y el worker arranca automáticamente con el backend (cada 1 min) — cualquier `envio` `encolado` en la BD de dev se enviaría de verdad. La lógica de negocio (encolar/dedup/opt-out/worker/reintentar/plantillas/webhook, 19 tests) se verificó con `EMAIL_BACKEND=console` forzado por `conftest.py`, nunca contra SendGrid real. La verificación contra el stack real (`docker compose`) se limitó deliberadamente a lecturas y RBAC (`GET /plantillas`, `GET /envios` vacío, `POST /plantillas/.../preview` — renderiza pero no envía, gating 403/200 por rol) — **sin crear citas/cupones/entregas de prueba contra la BD de dev real**, para no disparar un envío real de SendGrid solo por verificar el flujo. Se confirmó además, leyendo los logs del contenedor, que ningún envío real ocurrió durante la sesión de build.
